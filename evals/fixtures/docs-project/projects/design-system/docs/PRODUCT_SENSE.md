# PRODUCT_SENSE — 定性的な品質判断

この分野の「良い」を言語化する。必須仕様、数値合格条件、コマンド、現在状態は置かない。
それらは`PROJECT.md`、`docs/DESIGN.md`、`docs/QUALITY_SCORE.md`、`STATE.md`が所有する。

## What good looks like

- 初見の実装者が、迷わず1つの部品を選べる。
- 例外を足さずに要求を満たせている。

## Core beliefs

- 一貫性は見た目ではなく、判断の再現性から生まれる。
- 早すぎる抽象化は、後からの分割より高くつく。

## トレードオフ

- 柔軟性と一貫性が衝突したら、まず一貫性を採り、必要になってから逃げ道を足す。
- 実装速度のための一時的な逸脱は、期限と戻し方を添えたときだけ許す。

## Anti-patterns

- 使用条件のないバリアントを増やす。
- 「なんとなく揃っていない」という理由だけで既存部品を作り直す。

## 良い例と悪い例

- 良い: 3画面で同じ選択が再現できたので、patternsへ昇格させた。
- 悪い: 1画面のためだけにprimitivesへ表示分岐を足した。

## レビュー時の問い

- この部品を選ばなかった場合、どの部品が候補になるか。
- 判断の根拠は、次の担当者が同じ結論へ辿り着ける形で書かれているか。

## 見直し条件

- 逸脱が3件を超えたとき。
- 対象プロダクトが増減したとき。
