# projects/ — 長期的な仕事・成果契約・現在状態の正本

データや成果物を伴う固有プロジェクトを、1プロジェクト1ディレクトリで保存する。

## 二つの正本

```text
PROJECT.md = なぜ行い、何を実現するか。種別、成果契約、判断原則、固定制約を持つ
STATE.md   = 今どこにいるか。現在の目標、合格条件、有効な決定、次の一手を持つ
```

目的を持つ別の `GOAL.md`、現在地を持つ別の `STATUS.md` や `TODO.md` は作らない。
同じ情報の正本を二つにしない。詳細な時系列履歴は `runs/` またはGit履歴へ置く。

## Knowledge・Skillとの分離

```text
Knowledge = 何が分かっているか（証拠・背景・仮説・反証）→ knowledge/
Skill     = どう分析するか（手順・判定・出力契約）      → skills/
Project   = 何を作り、何を残したか（入力・成果物・記録）→ projects/
```

成果物を Knowledge・Skill・`.tmp/` に残さない。
逆に、プロジェクトから生まれた再利用可能な知見は `knowledge/` へ移す。

## 新しいプロジェクトの作成

`_template/` をコピーして作成し、最初に `mode` を決めてから `PROJECT.md` と `STATE.md` の
プレースホルダーをすべて書き換える。

```text
project-name/
├── PROJECT.md          # 成果契約 — 目的・種別・ゴールまたは使命・判断原則・検証方法
├── STATE.md            # 現在状態 — 現在の目標・合格条件・決定・次の一手・検証結果
├── inputs/             # このプロジェクトだけで使う入力 — 必要な場合のみ
├── outputs/            # 完成した成果物 — 必要な場合のみ
├── runs/               # 保存価値のある実行記録 — 必要な場合のみ
├── candidates/         # Project固有の再利用候補 — 必要な場合のみ
└── scripts/            # Project固有の固定コード — 必要な場合のみ
```

すべてのプロジェクトが全ディレクトリを持つ必要はない。必要なものだけを置く。
ただし、保持するすべてのプロジェクトに `PROJECT.md` と `STATE.md` は必須とする。

## Projectの種別

`PROJECT.md` の `mode:` は次の二つだけを使う。

### `finite` — 有限Project

一つの検証可能な終了状態を実現する仕事。`PROJECT.md` に「最終ゴール」と「完了条件」を置く。
全完了条件を検証したら `status: completed` とし、追加改善を惰性で続けない。
次のゴールは、新しいProjectまたは利用者が明示した次フェーズとして扱う。

### `continuous` — 継続運用

事業、プロダクト、メディア、長期運用エージェントなど、現在の目標を更新しながら続ける活動。
`PROJECT.md` に「継続的使命」「成功指標」「見直し・終了条件」を置き、達成可能な現在の目標は
`STATE.md` だけが所有する。現在の目標を達成してもProject自体を `completed` にしない。

`_template/PROJECT.md` の上部を次の形にし、「判断原則」以下の共通節はそのまま残す。

```md
---
name: <project-name>
status: active
mode: continuous
---

## 目的

<継続運用する理由>

## 継続的使命

> <どんな価値を誰へ提供し続けるか>

## 成功指標

- <継続的な健全性を判定する指標>

## 見直し・終了条件

- <目標や運用を見直す周期>
- <停止または廃止を判断する条件>
```

`finite` と `continuous` の区別がつかない場合は、作業開始前に利用者へ確認する。
AIが実装都合や目標達成を理由に `mode` を変更してはならない。

## 着手から終了まで

### 1. 着手

作業前に `PROJECT.md` と `STATE.md` を最後まで読む。現在の目標と合格条件、それが前進させる
完了条件または成功指標を一つ以上特定する。対象Projectが一つに定まらない場合や、依頼が
目的、成果契約、判断原則、非ゴール、固定決定と矛盾し、利用者が契約変更を明示していない場合は、
成果物を変更する前に利用者へ確認する。

### 2. 実行

成果物の作成自体ではなく、現在の目標と `PROJECT.md` の成果契約を満たす結果を目的にする。
品質基準や検証方法を弱めて完了扱いにしてはならない。個別タスクを理由に、`mode`、目的、
最終ゴールまたは継続的使命、完了条件または成功指標、判断原則、非ゴール、制約・固定決定を変更してはならない。
依頼が実行を含む場合は、計画や下書きで止まらず、ブロッカーがない限り検証と状態更新まで完遂する。

### 3. 検証

完了報告前に `PROJECT.md` の検証方法と現在の目標の合格条件を実行する。
完了条件または成功指標ごとに、コマンド結果、成果物、対象URL、利用者確認など
第三者が追跡できる証拠を確認する。

- 検証済みの事実だけを `STATE.md` の「検証結果」に置く。
- 実行していない検証は合格と推測せず、「未完了・ブロッカー」または「未検証事項」に置く。
- 検証が失敗した場合は完了扱いにせず、失敗理由と次の一手を残す。
- 外部公開、送信、課金、権限変更など利用者の承認が必要な操作は、未承認のまま完了条件を満たしたとしない。

### 4. 終了

状態が変わった場合は、成果物と同じ作業内で `STATE.md` を更新する。
`STATE.md` には現在有効な情報だけを残し、古い状態を本文へ積み増さない。
有限Projectの全完了条件を検証した場合は `PROJECT.md` の `status` を `completed` にする。
その際は `STATE.md` の現在の目標を「なし（Project完了）」、次の一手を「なし」とし、
「検証結果」へ全完了条件の証拠を残す。
継続Projectでは、現在の目標を達成しても `status` を変更せず、更新規則に従って次の目標へ進む。
最終報告では、達成した結果、検証証拠、未完了・ブロッカー、`STATE.md` 更新の有無を区別する。

## PROJECT.mdの変更

`PROJECT.md` の `mode`、目的、最終ゴールまたは継続的使命、完了条件または成功指標、
判断原則、非ゴール、制約・固定決定は、利用者が変更を明示した場合だけ変更する。
変更時は相互の矛盾を解消し、`STATE.md` の現在の目標・合格条件・有効な決定・次の一手も
同じ作業内で整合させる。

有限Projectの完了条件は普通の箇条書きで安定した合格条件を列挙し、達成記号を付けない。
条件ごとの達成状態と証拠は `STATE.md` の「検証結果」だけに置く。
継続Projectの成功指標も、数値の現在値や時系列履歴を `PROJECT.md` に書き込まない。

状態の `active` / `paused` / `completed` / `retired` は `PROJECT.md` のYAMLフロントマターだけが所有する。
`STATE.md` に別のプロジェクト状態を重複させない。

## STATE.mdの更新

- 現在の目標は一つの到達状態として書き、作業の羅列にしない。
- 目標の合格条件は第三者が判定できる条件にする。
- 検証結果には、確認日、対象、方法、客観的な結果をまとめ、現在判断に必要な最新の証拠だけを書く。
- 現在有効な決定には、今も作業を拘束する決定と根拠だけを書く。
- 失敗・却下済みには、方法、理由、再検討できる条件を書く。同じ方法を無条件に再試行しない。
- 次の一手は、現在の目標を前進させる最優先の一つに絞る。
- 不明な状態を推測で埋めない。「不明」「未検証」と明記する。

## 現在の目標の更新

AIは、現在の目標の合格条件を検証し、次の目標が `PROJECT.md` または `STATE.md` で
事前定義されているか、決定済みの順序から一意に定まる場合だけ、自動で次の目標へ更新できる。
更新時は、達成証拠、次の目標、その合格条件、成果契約との関係を同時に `STATE.md` へ反映する。

次の目標に新しい戦略、優先順位、予算配分、品質上のトレードオフが必要な場合は、
AIは候補と根拠を提示できるが決定しない。利用者の決定までは、現在の目標を未設定のまま
推測で埋めず、ブロッカーとして記録する。

## 既存プロジェクトの移行

既存Projectは次回の成果物変更前に、有限か継続かを判定して `PROJECT.md` に `mode` を追加する。
`STATE.md` がなければ `_template/STATE.md` を基に作成し、旧「現在の作業目的」は「現在の目標」と
「目標の合格条件」へ分け、旧「完了済み」は現在判断に必要な「検証結果」へ圧縮する。

`PROJECT.md`、成果物、`runs/`、Git履歴など確認できる証拠だけから現在状態を復元し、
確認できない目的、完了、決定、失敗を推測しない。`mode` の判断が曖昧な場合は利用者へ確認する。
移行だけを理由に最終ゴールや継続的使命を変更しない。

## コードと実行記録

コードの段階と片付けは `AGENTS.md` に従う。このProjectの再利用候補は `candidates/`、
固定コードは `scripts/` が所有する。`runs/` には保存価値のある実行記録だけを置く。

## 状態と廃棄

各プロジェクトのライフサイクル状態は `PROJECT.md` 冒頭のYAMLフロントマターの `status:` で管理する。
値は次の4つのみ。

- `active` — 進行中。
- `paused` — 停止中。再開の可能性があるため削除しない。
- `completed` — `finite` の全完了条件を検証済み。成果を保持し、追加作業を行わない。
- `retired` — 廃止決定済み。削除してよい。

`continuous` に `completed` は使用しない。`completed` の有限Projectを再開・拡張する場合は、
利用者が新しいProjectまたは次フェーズを明示する。AIが完了済みProjectを自動で `active` に戻してはならない。

削除はディレクトリごと `git rm` し、理由をコミットメッセージに残す。

```text
chore(retire): drop <project-name> — <理由>
```

アーカイブディレクトリは作らない。ゴミ箱はGit履歴に一本化し、復元も履歴から行う。
